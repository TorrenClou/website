## Why one container

TorrentDrive runs nine processes and two datastores inside one container image. Shipping them together
is a deliberate trade-off: a self-hoster runs a single command instead of wiring up five containers,
the torrent worker and cloud upload workers share `/data/downloads` without cross-container volume
mounts on PaaS platforms, and there is zero version skew between API, workers, and UI.

If you prefer a multi-container topology on your own Docker host, use
[`compose/docker-compose.split.yml`](https://github.com/TorrentDrive/deploy/blob/main/compose/docker-compose.split.yml).

## What runs inside

Supervisord manages nine programs:

| Program | Port | What it does |
|---------|------|--------------|
| `postgres` | 5432 | PostgreSQL 15. Bound to `127.0.0.1`, never published |
| `redis` | 6379 | Cache, resumable upload checkpoints, cancellation signals, progress streams |
| `api` | 47200 | ASP.NET Core API, `/metrics`, and `/hangfire` dashboard |
| `frontend` | 47100 | Next.js App Router (standalone output) |
| `torrent-worker` | - | Downloads torrents via hardened MonoTorrent engine (`torrents` queue) |
| `gdrive-worker` | - | Streams completed files to Google Drive (`googledrive` queue) |
| `s3-worker` | - | Streams completed files to S3-compatible storage (`s3` queue) |
| `prometheus` | 47600 | Scrapes OpenTelemetry Prometheus metrics from API & workers |
| `grafana` | 47500 | Pre-provisioned observability dashboards |

To inspect the live state of all nine processes:

```bash
docker exec torrentdrive supervisorctl status
```

## Startup

`entrypoint.sh` runs four steps before handing control to `supervisord`:

1. **Generates secrets** into `/data/postgres/secrets.env` on first boot — database password, JWT
   signing key, NextAuth session secret, and `GRAFANA_ADMIN_PASSWORD`. Any variable explicitly passed
   in the environment takes precedence.
2. **Initializes PostgreSQL** if `/data/postgres` is empty, then syncs the database user's password
   on every boot.
3. **Reads instance settings** — Hangfire worker concurrency and observability toggles — from the
   `SystemSettings` table so changes saved in the UI **Settings** page apply on restart.
4. **Exports runtime configuration**, mapping flat environment variables into the `Section__Key`
   hierarchy expected by .NET configuration providers.

## How a torrent becomes a file in your cloud storage

1. **Analyze (`TorrentAnalysisService` + `UdpTrackerScraper`)**: You upload one or more `.torrent`
   files. The API parses the Bencoded metadata and scrapes both **BEP 15 UDP** and **BEP 48 HTTP/HTTPS**
   trackers in parallel with bounded 2.5s DNS/socket timeouts.
2. **Enqueue (`HangfireJobOrchestrator`)**: You select which files to download and choose a storage
   profile. The API creates a **Job** record and dispatches `ITorrentDownloadJob` directly onto the
   Hangfire `torrents` queue (`[Queue("torrents")]`).
3. **BitTorrent Download (`TorrentDownloadJob`)**: `torrent-worker` downloads the selected files into
   `/data/downloads/<jobId>`:
   - **Protocol Encryption (MSE/PE)**: Prefers `RC4Full` / `RC4Header` stream encryption (or enforces
     strict RC4-only mode when `TORRENT_REQUIRE_ENCRYPTION=true`).
   - **Private Tracker Isolation (BEP 27)**: When `torrent.IsPrivate` is true, DHT, Peer Exchange
     (PEX), Local Peer Discovery (LPD), and public fallback trackers are completely disabled.
   - **Cloud VPS Hardening**: Disables UPnP/NAT-PMP port-forwarding probes and RFC 1918 local multicast
     broadcasts so datacenter security monitors are never triggered, and uses partial `.!mt` files so
     unselected boundary pieces never pollute your upload directory.
4. **Upload Dispatch**: When the download completes, `HangfireJobOrchestrator.EnqueueUploadJobAsync`
   inspects the destination profile's `ProviderType` and enqueues `IGoogleDriveUploadJob` (`googledrive`
   queue) or `IS3UploadJob` (`s3` queue).
5. **Cloud Streaming & Failover (`StorageTransferOrchestrator`)**: Both upload workers delegate the
   transfer lifecycle to a single deep module, `StorageTransferOrchestrator`, which handles:
   - Pre-flight storage health verification and automatic destination rerouting (`IStorageProfileRouter`).
   - Streaming resumable uploads through the provider-specific `IStorageDestination` adapter (`GoogleDriveUploadService` or `S3UploadService`) with Redis checkpointing and cancellation polling.
   - Automatic failover to another healthy drive when an upload hits quota, auth expiry, or repeated
     transient errors.
   - Post-upload local directory cleanup (`/data/downloads/<jobId>`) when `DeleteAfterUpload` is enabled.

## Backend Clean Architecture & Deep Modules

The .NET 9 backend (`TorrentDrive.sln`) is organized around deep modules with narrow interfaces
(documented in `backend/GLOSSARY.md` and `backend/docs/adr/`):

- **`TorrentDrive.Core`**: Domain entities (**Job**, **Storage Profile**, **Torrent**, `SystemSettings`),
  enums, DTOs, and narrow service contracts (`IJobOrchestrator`, `IJobExecutionTracker`,
  `IStorageDestination`, `IStorageProfileRouter`).
- **`TorrentDrive.Application`**: Business orchestration (`JobService`, `TorrentService`,
  `TorrentAnalysisService`, `UdpTrackerScraper`, `StorageProfileRouter`, `SettingsService`).
- **`TorrentDrive.Infrastructure`**: EF Core (`AppDbContext`), Hangfire dispatch
  (`HangfireJobOrchestrator`), worker execution tracking (`JobExecutionTracker`), unified cloud
  transfer orchestration (`StorageTransferOrchestrator`), and provider upload strategies.
- **`TorrentDrive.API` / `TorrentDrive.Worker` / `TorrentDrive.GoogleDrive.Worker` / `TorrentDrive.S3.Worker`**:
  Host processes sharing service registration and OpenTelemetry instrumentation via
  `TorrentDrive.ServiceDefaults`.
